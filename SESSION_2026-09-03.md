## 1. Splash — three separate bugs, three separate causes

The splash took the longest and produced the most useful findings. All three were misdiagnosed at
least once before being measured.

### Grey rectangle around the video

**Not the artwork.** A frame extracted from the clip and decoded showed pure `#FFFFFF`.

**Cause: H.264 colour range.** Video is normally encoded *limited range* (luma 16–235), and the
player is meant to expand it to 0–255 on playback. Android's pipeline often does not, so white
stored as 235 renders as **`#EBEBEB`** — a light grey box on a white ground.

**Fix:** the clips were re-encoded **full range** (numpy BT.709 → `-color_range pc -x264opts
fullrange=on`). Verified independently by parsing both the H.264 SPS VUI and the container `colr`
box.

> A parser bug of mine reported "no `colr` box" on the first full-range file and sent us down a
> dead-end WebM path. Child boxes inside an `avc1` sample entry start **78 bytes** past the header;
> I was reading from the wrong offset.

### Black box over the animation

**My bug, not the video's.** Animating opacity on a view containing a `TextureView` promotes it to
a hardware layer whose backing is **opaque black**, so every fade blended the video toward black
instead of the ground behind it.

Each mitigation made it worse, because each one animated alpha across the video.

**Fix — the rule now documented at the top of `SplashAnimation.tsx`:**

> **Never animate alpha on, or above, a `VideoView`.**

The video sits at opacity 1 for its entire life; an opaque white **cover** above it is animated
instead. `surfaceType="textureView"` stays and is load-bearing — a `SurfaceView` punches through
the hierarchy and ignores parent opacity entirely.

### Black frame at startup

`AppTheme` inherits `Theme.AppCompat.DayNight.NoActionBar` and never set `android:windowBackground`,
so between the native splash hiding and React Native's first frame, AppCompat's **dark** default
painted. Now set explicitly to white in `styles.xml`.

### Timing

Clip is 1.5 s intro + six icons at 1.15 s = 8.4 s. Played at `PLAYBACK_RATE = 1.2`
(~7.0 s), with `SPLASH_MIN_MS = 7000` derived from it. **Change one and the other must follow**, or
the animation is cut.

1.2× is a ceiling, not a preference: a 0.85 s-per-icon variant was rejected on 3 Sep, and 1.35×
lands exactly on it.

## 2. UI — Bold Cards, then Glass Light

Two complete rewrites. Bold Cards (`48a775c`, `8abbf66`) was replaced by the Glass Light code drop
(`d10e346`).

**No native modules were added, deliberately.** The Glass Light drop asks for `react-native-svg` and
`react-native-linear-gradient`; both would force an APK rebuild that the broken x86_64 toolchain
cannot produce. Instead:

| drop wanted | used |
|---|---|
| `react-native-svg` | `@expo/vector-icons` — already a dependency |
| `react-native-linear-gradient` | a **generated PNG** mesh (`assets/images/glass-mesh.png`) |

The PNG is written by a hand-rolled encoder (IHDR/IDAT/IEND + CRC32, zlib scanlines) with the blobs
blurred by three box-blur passes. This is *better* than the drop manages — its own comment concedes
the blobs are hard-edged because *"plain RN has no CSS filter: blur equivalent"*.

### Cards are white on purpose

The template specifies `rgba(255,255,255,0.55)` over the mesh, and its own mockup measures
`#E7EDFF`–`#F3F3FF` inside the cards — a lavender tint by design, which on a real screen reads as
grey panels with a grey rim. Solid white was wanted instead, so `src/theme/glass.ts` **departs from
the reference on purpose** and says so in comments. Chip fill (`#F3F3FF`) is sampled from the
mockup's own stat chip, since 50 % white over a white card would vanish.

### Tab bar

Two fixes: `insets.bottom` added to height *and* padding (edge-to-edge draws under Android's
navigation bar), and the labels given `lineHeight: 15` + **`includeFontPadding: false`** — custom
fonts carry extra intrinsic padding on Android, which was clipping the descenders.

## 3. Data honesty — what is deliberately absent

An API audit established the template was designed against a richer backend than exists. These are
omissions with reasons, not oversights:

| template element | why it is not drawn |
|---|---|
| Today's earnings, bonus, tips, payout | **no pay model in Odoo at all** |
| Rider rating | `Rider` has six fields, none a score |
| Distance, ETA, "You earn" per order | no such fields in the contract |
| Cash to deposit | `/orders` is active-only, so no aggregate is derivable |
| Order history | no history endpoint — a delivered job leaves `/orders` |
| Decline on a job offer | `offered` allows only `accept`; riders cannot refuse |
| Hub, Vehicle, Documents Verified | not on `Rider` |
| Notification-sound / Language toggles | no settings store, no i18n |
| Notification bell | nothing registers for push, so it would be dead |

Home shows the four `OrderCounts` where earnings sat. Earnings states plainly that payouts are not
set up. Orders lists **work in hand**, not history.

The job screen renders **three layouts from one route**, chosen by whichever action Odoo offers —
offer / en-route-over-map / green handover. The action machinery is untouched: `applyResult`, the
409 `override`, tracking started only on `tracking.enabled`, and the reset that stops one job's
buttons leaking into the next.

## 4. Push notifications

Mirrors the working implementation in `C:\Projects\KRA_KPI` — same Odoo team, same Expo SDK.
Expo push service, with Firebase as the delivery pipe.

**Built:** `src/push/register.ts`, `src/push/usePush.ts`, two `ApiAdapter` methods, the foreground
handler and listeners in `app/_layout.tsx`, and unregister-on-sign-out.

**Two details carried over from KRA_KPI:**

1. **`project_id` is sent with the token.** Expo rejects a send whose messages span two EAS
   projects — and rejects the *whole* request, so one stale token can silence every rider.
2. **Unregister before disconnect**, while the session can still authenticate the call. Same
   ordering rule as `stopTracking()`.

**Config done:** `google-services.json` (registers `com.alphalize.deliverypartner` inside the
existing `kra-kpi-3efd5` project), `googleServicesFile` in `app.json`, `extra.eas.projectId`, and
the FCM V1 service-account key uploaded via `eas credentials`.

> ⚠️ **The service-account private key was sitting in the project root, not gitignored, while
> `git add -A` was being used to commit.** It had not been committed. `*-firebase-adminsdk-*.json`
> is now in `.gitignore`. That key is shared by all four apps in the Firebase project.
>
> `google-services.json` **must** be committed — EAS Build only uploads git-tracked files.

**Still blocked:**

- `/api/delivery/push/register` and `/unregister` do not exist. The Odoo team can adapt
  `kpi_push_token.py`, which already has `upsert`, `deactivate`, `tokens_for_users`.
- Odoo sending on job-offered, grouped by `project_id`.
- **Remote push cannot work in Expo Go** — removed on Android in SDK 53. Needs a dev build or
  standalone APK. Local notifications work fine.

## 5. "noti test" — the device-test trigger

Saying **`noti test`** runs the full USB flow with no questions asked:

1. `adb devices -l`
2. Screenshot each screen (`adb exec-out screencap -p`) and read the PNGs
3. Tap **Profile → Send test notification** via `adb shell input tap`, screenshot the banner,
   background the app, fire again and tap through to the job
4. `adb logcat` filtered for `[push]`

Prerequisites: USB debugging on, Expo Go open on the app, Metro running.

The **Send test notification** button lives in a `__DEV__`-only diagnostics card in Profile. It
fires a *local* notification — never touches FCM — so it works over the Expo QR with no rebuild,
and proves permission, the Android channel, the foreground banner and tap-to-open-order.

In Expo Go the token line will report no token. **That is correct behaviour**, and worth seeing:
it proves the graceful-degradation path rather than a crash.

## 6. Environment gotchas

- **Build `arm64-v8a` only.** The x86_64 CMake toolchain fails at
  `:expo-modules-core:configureCMakeDebug[x86_64]` with `CMAKE_C_COMPILER not set`, and one bad ABI
  sinks the whole run: `./gradlew.bat assembleDebug -PreactNativeArchitectures=arm64-v8a`
- **Backgrounded Gradle dies silently here.** Check the **APK timestamp**, never the exit code —
  it reported success while producing nothing more than once.
- **Source files are CRLF.** Multi-line anchors in patch scripts must normalise to `\n` first;
  several edits half-applied before this was spotted.
- **`tsc` has OOM'd.** Use `NODE_OPTIONS=--max-old-space-size=4096 npx tsc --noEmit`.
- **No ffmpeg / Python-CV / ImageMagick.** Video cannot be decoded here — ask for **screenshots**,
  not screen recordings. PNGs *can* be decoded in Node via built-in `zlib`, which is how the colour
  sampling in this session was done.
